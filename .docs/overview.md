# Overview — current state (2026-10-12)

Describes the project **as it is now**. The target design, roadmap and rule exceptions are in `plan/roadmap.md`; the API contract is in `plan/backend-api.md`. Coding rules are in `../.claude/rules/architecture.md`.

## Overview
Endless Winter is a single-player Unity client (Unity 6000.5.7f1, Built-in RP, Android IL2CPP ARM64) that remakes the Whiteout Survival FTUE. Player state is owned by a server: today the engine-free `GameServer` (`EW.ServerCore`) runs in-process and saves to `persistentDataPath/player_save.json`; a .NET server will host the same code later. Game code is hot-updatable with HybridCLR and is delivered with Addressables.

Dependencies: `EW.Game → EW.Client.Core → EW.ServerCore → EW.Domain → EW.Contracts`. `EW.Client.Core` references ServerCore only to host the local server.

### Scenes
- `Loading` is the only scene in Build Settings, and it runs the Launcher.
- `Login` and `Tutorial` are Addressable scenes in the `Scenes_Core` group.
- `Exploration` is loaded additively.
- The Tutorial scene is generated by `TutorialSceneBuilder`.

### Runtime composition (per scene)
- `GameRoot` (MonoBehaviour, execution order -100) builds a `GameContext` in `Awake` from plain-C# services:
  - `GameSession`, `HeroRoster`, `BuildingRegistry`, `ExplorationService`.
  - City services: `BuildingService` → `FurnitureService` → `SurvivorService` → `WeatherService` → `FurnaceService` → `RecruitmentService` → `ChapterMissionService` → `CityProgressService`.
  - Then `PanelRegistry`, `StormWoodTracker` and `ChapterRewardsTrigger`.
  - Services get dependencies and a `NowMs` clock through constructors.
- Views implement `IGameBinding.Bind(ctx)`. The scene builder lists them on `GameRoot`, which binds them in order.
- Panels are Addressable prefabs (`UI_Panels` group), created through `PanelRegistry` under an inactive `PanelStaging` parent.
- Scene directors: `FtueDirector` (chapters 1–3), `ChapterFourDirector`, `ExplorationFlow`.

## Data flow
1. **Boot:** Loading → `HotUpdateBoot` downloads and loads hot code (CDN `ServerData/`, dev profile `CdnUrl`) → `GameEntry.Start` → Login (guest login) → Tutorial.
2. **Player action:** tap → view → service method → `ClientState.ExecuteAsync(IGameApi command)` → the local `GameServer` runs the rule on its own state and answers `CommandResult {rev, delta, events}` → `ClientState` applies the delta to the mirrors (a revision gap triggers a `GetPlayer` resync) → C# event → views refresh. The client never uploads player state; there is no `SavePlayer` (task 040). The service also raises `TutorialSignals` with `SignalNames` constants, and the FTUE director or missions wait on those signals.
3. **Time:** the services' `NowMs` clock. Building and furniture timers store absolute end times. Weather timers and older code still use `Time.unscaledTime`.
4. **Config:**
   - Original Lua JSON (`../ResourcesExport/Config`) → `../tools/config/*.py` → `Data/<Feature>/` JSON → editor importers → ScriptableObjects (e.g. `RecruitmentConfig`, `HeroCatalog`).
   - Service settings are serialized on `GameRoot`.
5. **Save/load:**
   - The server is the only writer: `GameServer` stores `PlayerSave` through `IPlayerStore` (`persistentDataPath/player_save.json`) after each accepted command or heartbeat. Pause and quit save nothing on the client.
   - `GameSession` and the feature services are mirrors loaded from `GetPlayer`; `CityProgressService.Begin` only restores them and enables chapter 4/vitals.
   - The FTUE step and tutorial checkpoints are server-owned (`PlayerSave` schema 11); `LegacyFtueMigration` moves old PlayerPrefs values once. Only the guest id stays in PlayerPrefs.
   - On load, earlier chapter state is rebuilt from the FTUE step (`ApplyStateFor`). Each owning service restores the city snapshot.

## Data models
- **Resources:** `ResourceType` and `ResourceAmount`, held in `ResourceWallet` (Domain), which is owned by `GameSession`.
- **City progress:** `CityProgressData` (Domain), a versioned snapshot of buildings, furniture, survivors, heroes and missions, saved together with the wallet. Schema 2 appends survivor vitals, `sickUntilMs`, `diesAtCure`, `inSickbed` and `savedAtMs`; schema 1 still restores (vitals start from config).
- **Survivor vitals (day/night):** `SurvivorService` steps every survivor once per `CityClock.MinuteChanged` through `SurvivorVitalsRules`, using `SurvivorDayNightConfig` (`Data/Survivors/SurvivorDayNight.asset`). It raises `SurvivorSick`/`SurvivorHealed`/`SurvivorDied`; a death removes the survivor. The model starts once chapter 4 is claimed (`CityProgressService`); before that the scripted chapter 4 illness (`Tick`) runs unchanged. On load it replays missed minutes, capped at `offline_work_max_ti`. `GameRoot` sets the `CityClock` schedule from the same config by Furnace level.
- **Config:** tables keyed by original int ids, e.g. building id `301` (furnace) and `building_302_1` signals.
- **Contracts are JSON for now** (`JsonUtility`, append-only field names). MessagePack int keys come when the package is reinstated; opcodes and keys are already assigned in `plan/backend-api.md`.

## External services
- **No remote game server, database or analytics yet.** The server runs in-process; login is a local guest provider.
- **Addressables remote content:** a static HTTP host serving `ServerData/` (dev: `python -m http.server 8086`).
- **Dev tooling:**
  - KitWright Unity MCP (local HTTP endpoint in `.mcp.json`).
  - `EndlessWinter/Dev/Server Dev Ops` window (Play Mode): grant, building level, FTUE step, skip stage, server clock
    offset, wipe player. Dev ops exist only when `GameServer.devOps` is on (editor and development builds).
  - Rejected commands raise `ClientState.Failed`; `CityHud` shows the `CommandErrorText` message as a toast.
  - LDPlayer running the original game as the behavior reference.
  - Python extractors in `../tools/`.

## Known gaps (from the plan, not proposals)
- Old patterns that are still present:
  - The static `TutorialSignals`, `BuildingFocus` and `GuideTarget` registries.
  - A few `Find*` fallbacks.
- The server accepts an exploration win by squad power; the fight itself runs on the client (roadmap §12, task 037). The FTUE still skips its battle (`FtueDirector.skipExplorationBattle`).
- See `plan/roadmap.md` §12 for exceptions.
